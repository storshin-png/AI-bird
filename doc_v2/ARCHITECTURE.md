Версия: 2.1
v2.1 — зафиксированы параметры окна анализа NN1 и распределение ответственности
Статус: MVP с 4 микрофонами, направлением источника, локальными треками и облачными картами миграции

## 1. Общая схема

```text
FIELD LAYER
Sensor #1 (4 mic N/E/S/W, Edge AI, DOA)
Sensor #2 (4 mic N/E/S/W, Edge AI, DOA)
Sensor #N (4 mic N/E/S/W, Edge AI, DOA)
        |
        | LoRaWAN / SD / LTE optional
        v

        |
        | HTTPS / MQTT

Ingestion → Processing Pipeline → Storage

        |
        v
APPLICATION LAYER
Web Platform + REST API + B2B Reports
```

## 2. Edge Layer

### Аппаратная часть

- MCU/DSP: ESP32-S3 или STM32H7 с внешним NPU при необходимости.
- Микрофоны: 4 MEMS-микрофона.
- Ориентация микрофонов: N / E / S / W.
- Аудио-интерфейс: I2S или PDM, 4 синхронизированных канала.
- Обязательная фиксация ориентации корпуса.
- Опционально: магнитометр.
- Питание: LiFePO4 + солнечная панель + MPPT.
- Хранение: microSD 32 ГБ или больше.
- Связь: LoRaWAN обязательно, LTE опционально.

### Программная часть

Прошивка реализует:

1. Постоянный захват 4 каналов.
2. Кольцевой буфер pre-roll.
3. FFT / спектрограммы.
4. NN1: bird / no bird.
5. Direction module: оценка азимута.
6. Local tracker: формирование трек-сегментов.
7. Запись 4-канального WAV.
8. Передачу телеметрии.
9. Служебную диагностику.

### Edge pipeline

```text
4-channel audio capture
→ circular buffer
→ FFT / feature extraction
→ NN1 bird detection
→ direction estimation (DOA)
→ local track grouping
→ 10s 4-channel WAV save
→ LoRaWAN telemetry
```

### Параметры окна анализа (единый конфиг)

NN1 выполняется скользящим окном по непрерывному потоку 4 каналов.
Параметры являются единым конфигом для прошивки и обучающего датасета.

| Параметр | Значение |
| --- | --- |
| Длина окна анализа | 2.5 сек |
| Частота дискретизации | 44.1 кГц |
| FFT-окно | 1024 отсчётов (~23 мс) |
| Hop спектрограммы | 512 отсчётов (~11.6 мс) |
| Оконная функция | Hann |
| Частотный диапазон | до 22.05 кГц |
| Представление | log-mel спектрограмма |
| Hop инференса — базовый | 1.0 сек |
| Hop инференса — adaptive | 2.0 сек |
| Hop инференса — высокая чувствительность | 0.5 сек |

Принципы:
- Окно скользит с шагом hop; перекрытие гарантирует, что короткий крик
  не будет обрезан на границе окна.
- Инференс запускается каждый hop; бюджет ≤ 300 мс оставляет запас
  на DOA, запись WAV и LoRaWAN.
- Изменение любого параметра окна требует синхронного обновления прошивки
  и обучающего датасета (новая версия датасета).
  
### Ключевые решения

- NN1 выполняется на edge.
- NN2 и NN3 выполняются в облаке.
- Direction estimation выполняется на edge.
- Локальный трек формируется на edge как предварительная оценка.
- Полный трекинг и фузия выполняются в облаке.
- Параметры окна анализа NN1 (длина окна, FFT, hop, оконная функция)
  являются единым конфигом для прошивки и обучающего датасета.

## 3. Direction Estimation

### Вход

- уровни сигнала по каналам N/E/S/W;
- время прихода;
- SNR;
- ориентация корпуса;
- метаданные установки.

### Выход

```json
{
  "event_id": "uuid",
  "azimuth_device_deg": 62.5,
  "azimuth_geo_deg": 152.5,
  "sector": "SE",
  "azimuth_confidence": 0.78,
  "bearing_quality": "good"
}
```

### Ограничения

- один датчик не дает точную позицию;
- направление является пеленгом;
- траектория строится вероятностно;
- несколько одновременных источников снижают уверенность.

## 4. Communication Layer

| Режим | Условия | Что передается |
|---|---|---|
| LoRaWAN-only | Нет LTE | Телеметрия, направление, track_id |
| LTE fallback | Есть покрытие | Телеметрия + аудио/архивы |
| Sneakernet | Полная изоляция | SD-карта с WAV |

### Протоколы

- MQTT для телеметрии.
- HTTPS для загрузки WAV.
- TLS 1.3.
- Уникальные device-сертификаты.

## 5. Cloud Layer

### Ingestion

- MQTT broker.
- API Gateway.
- Object storage.
- Validation service.
- Deduplication service.

### Processing Pipeline

```text
WAV → NN2 → NN3 → Open-Set → Result DB
Telemetry → Direction QA → Tracking Service → Track DB
```

### Direction QA

- проверка confidence;
- проверка согласованности с ориентацией датчика;
- фильтрация ambiguous bearings;
- повторный расчет направления при необходимости.

### Tracking Service

Трекинг выполняет:

- группировку событий по времени и датчику;
- объединение последовательных пеленгов;
- фузию данных от нескольких датчиков;
- оценку движения;
- расчет среднего направления;
- расчет уверенности трека;
- формирование геометрии для PostGIS.

### Storage

- PostGIS: геометрии датчиков, пеленгов, треков, миграционных слоев.
- TimescaleDB: временные ряды событий и телеметрии.
- S3-compatible storage: WAV, спектрограммы, архивы.

## 7. Data Flow

1. Датчик постоянно слушает 4 канала.
2. NN1 обнаруживает птичий голос.
3. Direction module оценивает азимут.
4. Гаджет записывает 10-секундный 4-канальный WAV.
5. Формируется локальный track_id при серии событий.
6. Короткая телеметрия уходит по LoRaWAN.
7. Рейдовая группа забирает SD или устройство передает WAV по LTE.
8. Облако запускает NN2 → NN3 → Open-Set.
9. Tracking service объединяет события.
10. Web обновляет карты направлений, треков и миграции.

## 8. Ключевые компромиссы

| Решение | Обоснование |
|---|---|
| NN1 на edge | Экономия энергии и трафика |
| NN2/NN3 в облаке | Слишком ресурсоемкие модели для MVP |
| 4 направленных микрофона | Позволяют получить направление без сложной антенной решетки |
| Direction на edge | Быстрая реакция, меньший объем передаваемых данных |
| Локальный трек на edge | Уменьшает облачную нагрузку и дает первичную траекторию |
| LoRaWAN + SD | Работает там, где нет LTE |
| Вероятностные треки | Один датчик не может дать точную GPS-траекторию |
| Open-Set | Защита от ложной классификации неизвестных видов |
```
