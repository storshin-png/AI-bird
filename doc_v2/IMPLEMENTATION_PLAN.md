## 1. Принятые решения

1. Рамка поставки — **4-месячный MVP** из `MVP_SPEC.md`: 8 спринтов по 2 недели. Заморожена 06.10.2026 и повторно не открывается. `Critical_Path_2.md` (8 месяцев, 100+ видов, LTE) сохраняется как план после пилота и в эту поставку не входит.
2. Перед спринтом 1 идёт **подготовка 2 недели**. В ней люди принимают решения и стенд, агенты собирают репозиторий, контракты и окружение.
3. Непосредственные исполнители — **ИИ-агенты**, среду которых выбирает владелец зоны. Люди ставят пакет, принимают артефакт по чеклисту и открывают pull request. В ветку `main` вливает CEO. Состав и порядок — `COLLABORATION.md` от 07.10.2026.
4. Железо пилота — **вариант 2 BOM** (ориентир ~$158, потолок `MVP_SPEC` ≤ $170): ESP32-S3 N16R8, 4× Knowles ICS-43434, LoRaWAN SX1262, магнитометр LIS3MDL, корпус ASA, PTFE-мембраны. Вариант 1 допустим только как стендовый макет. Вариант 3 и LTE в MVP не входят.
5. Первый содержательный заход после подготовки — три независимых пакета: схема БД и ingest, нарезка и NN1 v0.1 на открытых данных, каркас прошивки захвата 4 каналов. Карта датчиков подключается к синтетике и не ждёт полевого пилота.
6. Сквозной критерий интеграции — один синтетический прогон из `USERFLOW.md`: WAV → пакет телеметрии → облако → вид + пеленг + трек на карте.

## 2. Рамка MVP, которую агенты не расширяют

| Параметр | Значение |
|---|---|
| Окно анализа | 2.5 с, 44.1 кГц, FFT 1024, hop 512, Hann, log-mel |
| NN1 | edge, ≤ 500 КБ, ≤ 300 мс, F1 ≥ 0.90, ложные срабатывания ≤ 10% на чистом шуме |
| Пеленг | MAE ≤ 20° на чистом сигнале, ≤ 30° при SNR ≥ 10 дБ |
| NN3 | 50 видов региона, Top-5 ≥ 0.80 |
| Open-Set | отсекает ≥ 70% неизвестных звуков |
| Трек | вероятностный пеленг и фузия, без GPS-позиции птицы |
| Связь MVP | LoRaWAN-телеметрия + WAV на microSD |
| Пилот | 5 датчиков, 4 недели, обслуживание раз в 7 дней |
| BOM | ≤ $170, цель варианта 2 ~$150–158 |

Единый конфиг окна обязателен для прошивки, обучающего датасета и облачного пайплайна. Его меняет только CTO отдельным согласованным пакетом; изменение порождает новую версию датасета и модели (`TEAM.md`).

Вне MVP: идентификация особи, NN2 на устройстве, передача WAV в реальном времени, мобильное приложение, государственная сертификация, точная GPS-траектория, более 50 видов, оценка высоты полёта, OTA, ЕСИА, LTE.

## 3. Режим работы

### 3.1. Люди

Люди принимают решения, которые агент не может закрыть, и ставят статус «принято» или «вернуть».

| Ворота | Кто принимает |
|---|---|
| Список 50 видов, golden set, арбитраж `unsure`, биологический смысл треков | орнитолог |
| Заказ плат и компонентов, сборка, стенд, установка, съём SD | CTO + полевые операции |
| Лицензии записей, разрешения на локацию, LOI | CEO |
| Смена окна анализа, API и схемы БД | владелец контракта (CTO — окно; Lead Backend — API и схема) |
| Мерж в основную ветку | CEO. Автор запроса отмечает чеклист своей зоны |

Нагрузка людей — контроль, а не разработка. Ориентиры часов — в файлах `roles/`. Массовая разметка L1, обучение, схемы, прошивка, облако и веб-интерфейс выполняются агентами. Орнитолог лично закрывает golden set и спорные фрагменты. Полевая группа лично монтирует датчики и забирает носители.

### 3.2. Агенты

Базовое ТЗ облака и веба — `AI_AGENTS_SPEC.md`. Для этого плана оно распространяется на данные, обучение и прошивку: агент пишет и проверяет артефакт, человек принимает.

| Зона агента | Ревьюер |
|---|---|
| Agent DB, Agent Auth, Agent Backend | Lead Backend |
| Agent Pipeline (инференс, без обучения) | Lead ML + Lead Backend |
| Agent Tracking | Lead Backend + орнитолог |
| Agent Frontend | GIS-разработчик + Lead Backend |
| Агент данных и обучения (NN1, DOA, NN2, NN3, Open-Set) | Lead ML; виды и golden set — орнитолог |
| Агент прошивки | CTO |
| Агент аппаратной документации (схема, корпус, тест-план) | CTO |
| Агент полевых чеклистов и метаданных установки | полевые операции + орнитолог |

Правила из `AI_AGENTS_SPEC.md` §2 действуют для всех зон: один агент — одна зона; контракт первичен; параметры спектрограммы только из единого конфига; функционал за пределами `MVP_SPEC.md` не реализуется; каждый артефакт проходит ревью до мержа.

### 3.3. Пакет задачи

Агент получает пакет и не выходит за него.

1. Цель и спринт.
2. Входные документы и контракты.
3. Запрет расширять MVP и менять окно анализа, API или схему БД.
4. Чеклист приёмки.
5. Имя ревьюера.
6. Команда самопроверки (тест, миграция, отчёт метрик).

Статусы приёмки: **принято**, **вернуть** (список замечаний), **блок** (решение человека: лицензия, закупка, биология, допуск на локацию).

## 4. Контракты между треками

Трек считается согласованным, когда совпадают эти артефакты, а не когда совпали устные договорённости.

| Контракт | Где живёт | Владелец |
|---|---|---|
| `config/window_config.yaml` | репозиторий, единственный источник | CTO |
| Манифест фрагментов | `Структура разметки датасета.md` | Lead ML |
| Событие: `event_id`, пеленг, `local_track_id`, телеметрия | `ARCHITECTURE.md` §3, `MVP_SPEC.md` §2.1 | CTO + Lead Backend |
| Схема БД | `AI_AGENTS_SPEC.md` §4.1 | Lead Backend |
| OpenAPI | `/docs` бэкенда | Lead Backend |
| Пороги метрик | `MVP_SPEC.md` §3 | Lead ML (модели), CTO (латентность и размер NN1) |

`event_id` — UUID v4, создаётся на устройстве и проходит MQTT, REST и все таблицы без подмены.

## 5. Четыре трека

### 5.1. Данные и модели

Черновик лежит в `ml/`: нарезка, спектрограммы, сплит, валидация, обучение компактной CNN. Скрипты режут моно и держат конфиг копией в коде. Дальше их отвязывают от локальных путей и подключают к `config/window_config.yaml`.

Порядок: открытые записи → окна 2.5 с → очередь Label Studio → NN1 v0.1 на моно и открытых данных → стендовый датасет направления → NN3 и Open-Set на 50 видах → NN2 на синтетических смесях → дообучение на полевых 4-канальных записях пилота. Веса сдаются в ONNX вместе с отчётом метрик. Пока нет полевых каналов, облачный пайплайн работает на заглушках моделей.

### 5.2. Облако и веб

Порядок зависимостей из `AI_AGENTS_SPEC.md` §6:

| Спринты | Агенты |
|---|---|
| 1–2 | Agent DB → Agent Auth → Agent Backend (ingest и устройства) → Agent Frontend (карта датчиков) |
| 3–4 | Agent Pipeline на заглушке NN3 → Agent Tracking L0–L1 → слои пеленгов и треков |
| 5–6 | реальные модели → Tracking L2–L3 → очередь Unknown, экспорт |
| 7–8 | исправления, тесты, нагрузка, отчёт пилота |

Фронтенд разрабатывается на синтетическом GeoJSON.

### 5.3. Прошивка

Агент реализует захват 4 каналов, кольцевой буфер, инференс NN1, оценку направления, запись WAV и пакет LoRaWAN. До прихода плат тот же контракт гоняется на записанных WAV: размер модели, время инференса, байты телеметрии. Приёмка на ESP32-S3 — на стенде CTO.

### 5.4. Железо

Агент выпускает схему, разводку, модель корпуса и тест-план стенда. Физические платы, печать, пайка и установка делают люди. Комплектующие варианта 2 на **2 стендовых гаджета заказаны 06.10.2026**. Длинный цикл деталей под 5 пилотных датчиков ещё не заказан.

Стенд направления: известные азимуты, дистанции 5, 10, 20 и 50 м (`DATASET_STRATEGY.md` §4).

## 9. Риски, которые закрываются контролем

| Риск | Как проявляется для агентов | Действие людей |
|---|---|---|
| Train/inference mismatch | агент копирует FFT в код модуля | приёмка только при чтении `window_config.yaml` |
| Энергия 4 каналов | прошивка «всегда слушает» без adaptive hop | CTO принимает замер автономности на стенде |
| Ветер и ориентация корпуса | красивый MAE на синтетике | орнитолог и CTO принимают полевой набор с SNR и меткой ориентации |
| Ложные виды | высокая уверенность на неизвестном | Open-Set и выборка Unknown у орнитолога |
| Лицензии | загрузчик тянет всё подряд | CEO подтверждает список источников до обучения NN3 |
| Пилот зимой | модели учатся на весенних архивах | сезон утверждён 06.10.2026; до 16.10 остаётся локация в разделе 8 |
| Плата не приехала к спринту 2 | простой прошивки | трек прошивки продолжается на WAV-симуляторе; стенд сдвигается, софт не ждёт |
